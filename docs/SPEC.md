## 1. 一句话

模型自己挑位置、自己写摘要，插件只把四条宿主认识的记录写进会话日志；DSH 的界面、取回链、别的压缩后端都不需要知道我们存在。

## 2. 命名

| 项 | 值 |
|---|---|
| 插件显示名 | Ebbing Context |
| 包名 / bundle 行 id | `dsh-ebbing-context` |
| 日志文件 | `<DSH_HOME>/logs/ebbing-context.log` |
| 工具 | `context_map`、`compress`（只有这两个） |

**名字来源**：`ebbing` 是"渐渐消退"的意思，取它就是想说明这个插件在做什么——**模拟记忆的自然衰退**：越旧的内容分辨率越低，但不是删掉，而是逐层降级（原文 → L1 块 → L2 块 → L3 关键词）。名字只说这件事，**不要去蹭艾宾浩斯或任何学术出处**：那是给名字找靠山，不是描述机制，而且我们的降级是按需触发的离散分档，不是曲线。

包名、仓库名、显示名只用一串字（差别只有 `dsh-` 前缀），搜“ebbing context”命中的是同一个东西。

**曾用名**：`dsh-infinity-context`（显示名 `DSH-Infinity Context`）。2026-10-30 弃用：已有同名项目，且 `infinity` 只承诺"无限"、不描述机制。改名前从未装机、也从未推送，所以没有兼容负担；工具名 `compress` / `context_map` 与命令 `/context-status` 全程未动（它们模型可见，改了要连带改提示词并打穿前缀缓存）。

## 3. 挂载

- profile 的 `cordis.patch.yml` 里**一行 `insert`**，带完整 `config`；不实现、不替换任何宿主服务。
- 包结构按 `cordis-plugin-development` 的 `host-plugin.md` 办：`package.json` 声明 `dsh.bundle.patch`；`exports` 导出 `.` / `./locale/*.json` / `./icon`；`files` 含 patch、locale、icon、全部运行时文件。`locale/{zh,en}.json` 各带 `meta.title` + `meta.description`；`icon.svg` 是自绘的（同心横条：越靠上越短 = 越老越压缩）。
- `index.js` 只导出 `apply(ctx, config)` + `inject`；所有注册都包在 `ctx.effect()` 里，事件用 `ctx.on()`，由插件作用域负责清理。
- 硬依赖（缺了就不启动，且要给可读错误）：`tools`、`sessions`、`tokenMeter`、`agents`。
- 软依赖（`ctx.get()` 取，缺了降级）：`sessionProjections`（缺 `turnOutline` 投影时改扫日志里的 `turn/start`，见 `plugin/lib/blocks.js` 的 `turnsFromLog`；2026-10-30 P0-4 之前它是硬依赖，结果缺投影的装配里插件完全不能用）、`systemPrompt`（缺则不注入提示段）、`toolResultPruner`（缺则跳过剪枝）、`commands`（缺则不注册命令）、`goals`（缺则不执行 `disarm`，超限通知照发）。
- **不**注册 message projection（卸载会让旧会话拒绝派生）。台账将来用 state projection 做。
- 推荐同时把宿主的 `compaction-basic` 设成 `auto: false`：它的自动压缩会写八段式摘要把金字塔拍平。**2026-10-30 已核实本机 desktop profile 就是 `auto: false`**（`E:\AgentSupport\DeepSeek\profiles\desktop\cordis.patch.yml` 的 `- id: compaction-basic` → `config.auto: false`）；别的机器要自己确认，默认值是 `true`。
- 我们的 bundle patch **不去覆盖宿主的 `compaction-basic`**：那行在 `compaction` 这个 `group` 里，跨组按 id 覆盖会连带改宿主的隔离配置，风险大于收益；装机文档里改成"装机后确认这一项是 false"。

**装机只有两种能真跑起来的方式**（2026-10-29 只读审核，宿主源码）：

1. `dsh plugin add <插件目录>`——包进 profile 的 `node_modules`，patch 行的 `name` 是裸包名，由 ESM 解析找到它。
2. 或把包放到 profile 的 `node_modules` 下，且 patch 行 `name` 写 `./index.js`（`dsh-app-boot/lib/index.js:3974` 只对 `./`、`../`、绝对路径做 `pathToFileURL` 改写，裸包名不改写）。

**只把目录拷进工作区、patch 行写裸包名不算装好**：Loader 的 import 失败只写日志、不抛异常（`cordis-plugin-loader/lib/index.js:454-456`），界面上会看到这一行、但它从来没启动过，插件注册的工具和命令也都不存在。装机后先确认两件事：`compress` / `context_map` 两个工具在、`/context-status` 命令在。

配置页能不能出现另有条件：该行 fiber 必须处于 ACTIVE 且至少有一个 `volatile` 叶子（`dsh-settings/lib/index.js:413-419`），见 §21.1。

## 4. 表层与四区

发送给模型的消息按位置分四区，从上到下：

```
[system prompt]  [L3 区]  [L2 区]  [L1 区]  [L0 原文区]  [当前轮]
```

- **L3 区**：可多块；按表层顺序排列，越靠后越新——新压出的块追加在本区末尾，所以区内序号 1 是**最老**的那块。
- **L2 / L1 区**：各自若干摘要块，越靠上越老（序号 1 = 该区最老）。
- **L0 原文区**：还没被压过的真实对话，按时间顺序。
- **当前轮**：永远不压。

层级不是存下来的，是**算出来的**：一个块的层级 = 它盖住的那些节点里最高层级 + 1（盖住的全是原文 → L1）。

### 4.1 轮号怎么对齐（这条决定"会不会切错"）

轮号来自宿主的 `turnOutline` 投影（`{ turn, seq }` 列表，`seq` 是 `turn/start` 的事件号）。四件事必须分清：

| 概念 | 是什么 | 拿它干什么 |
|---|---|---|
| 轮号（`T19`） | 只用来在 `to` 里**指认**用户想压到哪一轮 | 解析后仍落到一个表层位置，落到哪里由下面的"地标"决定 |
| 地标（轮首位置） | 每轮第一个仍在表层上的原件节点的**下标** | 判断区间两端是否落在整轮边界上 |
| 界标算法 | 取"事件号 ≥ 本轮起点"的节点里事件号最小的那个，再取它的下标 | 抗原位替换（替换后事件号变成新的、更大的号，但位置没动） |
| 空节点（`节点数≠消息数`） | 宿主派生为 `null` 的空 `system`/`developer`/`assistant` 消息 | **逐个节点投影**拿到"这个节点有没有消息"（`session.log[seq]` + `session.deriveEventMessage(event)`），映射精确时照常按下标判区间与配对；映射拿不到时才退回整轮边界判断 |

**安全性质（比准确性更重要）**：界标算出来的位置，要么是某轮真正的第一个原件节点，要么是"后面某轮的第一个节点"——两者都是真起点，**永远不会落在某一对调用/结果的中间**。代价是标签会塌缩：某一轮的轮首被替换过（例如被压成检查点块，事件号跳到日志末尾）时，这一轮就没有地标了，区间把它并进相邻轮次、地图上的轮号偏粗——但不会切错。

**最后一条护栏**：`to` 只接受**已结束**的轮（`turn >= currentTurn` 一律拒），所以当前轮永远进不了区间；而"最后一轮"的边界本来会退化成表尾，也正好因此碰不到。

**拿不到轮次大纲时**（投影没挂载）：`l0` 直接说不可用，`l1`/`l2` 照常（它们用块序号，不需要轮号）；地图与报错都按这个说法给，不再说"没有原文"。

### 4.2 三条不自救的失效（审计 2026-10-29 补，全部只拒写、不猜）

上面那套算法本身是安全的，但它**依赖宿主给的大纲与消息表是对的**。有三种情况这两张表会骗人，插件一律拒绝 l0，绝不"猜一个差不多的位置"：

| 失效 | 怎么认出来 | 拒哪里 | 为什么不能猜 |
|---|---|---|---|
| 大纲缺轮/乱序（`T1,T2,T4`） | `readZones` 查轮号连续 + `seq` 严格递增（`outlineFault='gap'/'order'`） | l0 | 缺的那轮会被算进前一轮，`to:T2` 静默把 T3 一起压掉 |
| 当前轮在表层没有节点（大纲超前） | `turnStartIndex.get(currentTurn) === null`（`outlineFault='current'`） | l0 | 当前轮可能被判成"已结束"，压掉正在进行的轮 |
| 表层有空节点 **且** 已有压缩块 **且** 拿不到精确映射 | 消息数 ≠ 节点数、消息里出现块签名、且 `deriveExactly()` 返回 `null`（`zones.ambiguous`） | 全部 | 两张表对不上，块落在哪一行推不出来；真块会被当原文重压，旧摘要被压进新摘要里 |

**空节点本身不等于不可压（2026-10-30 更新，这条已从"永久死锁"变回"可压"）**：宿主并没有把这个能力藏起来——`session.log` 是公开字段（`ref/pkg-0.2.1-rc.3/dsh-session/index.js:504`/`:519`），`session.deriveEventMessage(event)` 是公开方法（同文件 `:555`/`:1694`），于是可以**逐个节点**问"你有没有消息"，得到精确映射，完全不需要"按下标对齐"这个前提。只要拿到映射：空节点被跳过、块照旧按块头认、区间与配对照常按节点算（`plugin/lib/blocks.js` 的 `deriveExactly()` / `messageFor()`）。只有映射也拿不到（`log` 不是数组、事件缺失、投影抛错）时，才退回"整表当原文 + 整轮边界"这条粗路径，并在那种状态下仍保留 `ambiguous` 的整批拒绝。**副作用**：`isTurnBoundaryPair` 对块起点恒假的那个隐患也随之消失——判缺精确映射时不再走那条路。

**块头轮号只有"查得出来才敢比"**：`l0` 建区间时会逐个看区间里的旧块，块头没有轮号（`T?`）或带 `+`（下限）就拒写——下限不能证明"这块在 `to` 以内"。**注意这条在现行实现里不可达**：`impureRange()`（`plugin/lib/compress.js:269-304`）先一步整段拒掉了"原文区间里夹着块"的情形（`plugin/lib/compress.js:188` 早于 `:196-215`），所以执行流到不了块头比较那一步。保留它是为了**将来若放宽 `impureRange` 的 l0 规则**（例如允许原文区间吸收外来检查点）时，这一层判断不需要重新设计；改动那一处时必须同时把这条恢复成可达，否则块头轮号错了会一代代传下去。

### 4.3 "会不会永久压不动"逐项排查表（2026-10-30 建，用户质疑"同一件事修了三轮"之后）

这张表的用处：以后任何人（包括审核员、包括我自己）怀疑"某条会话卡住了"，先照表对一遍，**不要再凭印象换一套思路重写**。前两轮的教训写在表后。

| 状态 | 怎么认出来 | 会不会让整条会话永久压不动 | 守卫 | 钉住它的测试 |
|---|---|---|---|---|
| 空节点 + 表层已有块 | `zones.ambiguous` | **正常不会**：`deriveExactly()` 逐个节点投影（`session.log[seq]` + `session.deriveEventMessage(event)`），空节点跳过、块照旧认；只有映射也拿不到时才拒 | `plugin/lib/blocks.js` 的 `deriveExactly` / `messageFor`；`compress.js` 的 ambiguous 早退 | blocks.test「有精确映射时不再报歧义 / 块照旧认得出 / 空节点既不进原文区、也不丢尾节点 / 按节点取消息」4 条 |

**表后的两条教训（写死，防止第四次换思路）**：
1. **先找接口，再设计修法**。前两轮的修法（`ebba05e` 的"整轮边界"、`4eb43c0` 的"明示 ambiguous 拒绝"）都建立在同一句错误断言上——"宿主没有非弃用的逐节点读取入口"。那句话是我只查了 `eventAt`/`snapshotEvents`/`ownEvents` 三个被弃用方法就下的结论，而 `Session.log`（公开字段）与 `Session.deriveEventMessage`（公开方法，带 JSDoc）一直都在。**结论下在"我没找到"之前，要再查一遍类定义本身。**

## 5. 四个键

`compress` 的参数是四个可选键，**键名 = 要压的那一层**：

| 键 | 压什么 | 产物去哪个区 | `to` 怎么写 |
|---|---|---|---|
| `l0` | L0 原文区的开头一段（**到 `to` 那轮结束为止，整轮**） | 变成一个 L1 块 | 轮号，如 `T19`（= 宿主写的 `turn 19`）；只能是已结束、且不在 `keepTurns` 保护圈里的轮 |
| `l1` | L1 区的开头几块 | 变成一个 L2 块 | 该区序号，如 `3`；**最多到「块数 − 1」**（最后一块永远不压） |
| `l2` | L2 区的开头几块 | **自成一块，落在 L3 区末尾；旧的 L3 块原样不动、不拼接** | 该区序号；同样是「块数 − 1」 |
| `l3` | 整个 L3 区 | 重写成一块更短的 L3 | 不收 `to`（整区） |

**`l0` 也必须有 `to`**——四个键里只有 `l3` 不收 `to`。"不带 `to` 压 l0"这个写法从来没有过，旧错误串里出现过一次已删除。

**每层最后一块不压**：它是这一层与新内容的接口，压掉之后这一层就没有"最新那一块"了（层与层之间的界限会塌）。所以 `l1`/`l2` 的 `to` 上限是「块数 − 1」，该区不足 2 块时就是"暂时没得压"。**`l3` 是例外**：它不收 `to`，一次把整个 L3 区压成一块（`plugin/lib/compress.js:244-251` 直接取 `zones.zones.l3` 的首尾，**不经过 `resolveZoneIndex`**，所以不受"最后一块"约束），哪怕只有 1 块也能压；`canCompressZone('l3')` 也按"非空"判。

**`keepTurns`（默认 2）**：原文区必须留住的最后 N 轮，`l0` 的 `to` 最多写到 `当前轮 − N`。当前轮本来就不在可压范围里；这条是给"最近几轮还在用、压了立刻要取回原文"留的缓冲。

每个键都要给 `title`（中文名词短语，≤ `title.maxTokens`，默认 50）和 `summary`（正文）。

**摘要正文固定四行**（写在 `compress` 的 `summary` 参数描述里，顺序不变、缺行留空、不另加小标题）：**用户意图** → **模型实际执行**（含没做成的、失败过的尝试与原因） → **运行结论**（成了什么/没成什么，附件把路径或地址写全） → **数据**（还要继续用的数值、标识符、路径与命令）。判断标准仍是"删掉这段之后下一轮还会做出同样的决定吗"，且禁跨块引用。**换掉旧骨架（结论/数据/未完/约束）的理由（2026-10-30，用户拍板）**：旧版只覆盖决策与事实，最容易丢的恰是"用户到底要什么"和"做成了什么、产出在哪"——这两项一丢，下一轮就会把已完成的工作重做一遍。

**级联是硬前提**（不是建议）：要给 `l3`，就得同批给 `l2`、`l1`、`l0`；给 `l2` 就得给 `l1`、`l0`；给 `l1` 就得给 `l0`。**只在那些层"还能压"时才要求**——判据是 `canCompressZone()`：`l0` 看是否还剩至少一个未被 `keepTurns` 护住的轮，`l1`/`l2` 看是否至少 2 块，`l3` 只要非空（与上面"l3 是例外"一致；三处口径必须相同，曾出现 `canCompressZone` 要 2 块而 `buildOp` 允许 1 块，导致级联少要一层、地图说不可压）。用"还有内容"当判据会把整批锁死：某层只剩 1 块（最后一块不压）时它永远压不了，级联就一直要求它。

## 6. `context_map`

每次决定压缩前调一次。返回四段：

1. **总量**：已用 / 窗口 / 百分比 / 是否估算。
2. **四区配额表**：每区已用、上限、百分比；超了标「已超设计容量（只影响提醒，不阻止压缩）」。
3. **块列表**：序号 · 区 · 盖住的轮次 · token · 标题。覆盖轮次后面带 `+`（如 `T16–T19+`）表示"这块盖到 T19 之后仍未封口"（块头写的就是 `T16–T19+`，见 §7），不显示 `+` 会让模型以为它只盖到 19。
4. **可压位置**：每区给出**可写范围与代价**，空的区写「暂不可用：该区为空」。措辞规则三条：
   - **只陈述事实**：可写范围（`to=T16–T18` / `to=1–4`）、落在表层上的锚点、当前第几轮、被 `keepTurns` 保护到哪。地图**不给建议、不给推荐值、不用形容词施压**（"极端情况""一般只""最好先"这类一律不用）。
   - **代价要对称地写**：写到最早那个锚点 = 只并一轮；写满 = 一次并掉 N 轮、细节只留在摘要里。两端都给，模型自己权衡。
   - 理由：插件的目的是**让模型自主判断该压哪里**，不是替它做机械判断。给"建议值"等于把决策收回到插件手里；给"上限"又会让模型把上限当目标。只有事实加代价，才是真的把选择权留在模型手上。

**地图不带任何流水号，过期与否由插件自己记**（`plugin/lib/license.js`）：取地图时在进程内 `Map` 里记一条 `{ gen: surface.replaceGeneration, count: surface.nodes.length }`（按 agentId），压缩前 `check()` 比 `replaceGeneration`——变了就说"这张地图已经过期了"，并让模型用"最近一次结果里附的新地图"（提醒、成功回执、拒绝回执都会带一张）。压缩成功 `consume()` 收证；**折叠（我们自己做的一次表层替换）之后要 `restate()` 把代数对齐**，否则会出现"压完一层 → 折掉调用记录 → 紧接着想再压一层被拒"的假过期（`6a0e134` 修）。这张证是进程内状态，**不随会话持久化，重启后模型第一次压缩前必须重新看地图**（提示语就是为这个写的）。

## 7. 一次压缩写四条记录

每个子事务，按顺序、**同一段同步代码里**：

1. `compaction/start`（`{compactionId, turn}`）
2. `compaction/summary`（`{compactionId, summary, shadowedRange, shadowedSeqs, shadowedTokenCount, provider, model}` —— 这里的 `summary` 是**未加框**的正文）
3. `user/message`（检查点消息，带 `surfaceOp: {op:'replace', startSeq, endSeq}` 与 `sourceEventSeqs`（含**每一个**被遮蔽节点），`source` 用 `{kind:'compact-checkpoint', compactionId}`）
4. `compaction/end`（`{compactionId, turn}`；出错也要写，带 `error`）

`provider` / `model` **恒写**：读不到路由时写空串，不要省掉这两个键。现行 v4 日志不校验它们，但旧日志升级到 v4 时会被 `assertReleasedEventPayload` 判缺字段拒掉（必填表在 `dsh-session-format-v0-to-v1/lib/index.js:60-74`，调用点 `:1919`）。

正文加框：`〔标题〕` + `CHECKPOINT_PREAMBLE`（宿主原文逐字节）+ `<compacted-summary>`…`</compacted-summary>` + 取回线索行。

多个键一起给时按**表层位置升序**落盘（先 l3；越靠上的越先写），每个子事务独立 `compactionId`。

**摘要会在上下文里存在两份（已知代价，不是 bug）**：模型这次写的 `summary` 既进了检查点块正文，也留在这轮 assistant 消息的 `tool-call` 参数里。参数那份要等这一轮被后续压缩遮蔽才会消失，在此之前每次请求都要为它付一次 token。因此：

- 收益校验只比较"被压内容"与"块正文"，**不含参数副本**——也就是说面板/回执上显示的省下多少，是扣掉块正文、但没扣掉参数副本的乐观值；
- 提交失败时参数副本同样留在表层且毫无收益，连续失败会累积，所以工具说明里要求"一次写对"；
- 这笔开销的**主解法是 `foldCallRecord`**（成功后把调用与返回折成一句短注，见本节末尾）；另两条退路是把 `segment.*` 调小，或让压缩更频繁（每压一次就会把上一轮的参数一并遮蔽）。

**"压缩成功后把调用参数就地缩掉"这条路，宿主不允许，别再试。**（2026-10-29 读源码确认，实现过一版又撤回）

| 事实 | 出处 |
|---|---|
| 替换任意表层节点时，事件的 `sourceEventSeqs` 必须覆盖每一个被遮蔽节点 | `ref/upstream/session-surface.ts:361-364`（`surface replace: sourceEventSeqs must include every shadowed surface node; missing …`） |
| 而 `assistant/message` **只要带 `sourceEventSeqs` 就直接抛错** | `ref/upstream/session-surface.ts:335-337`（`assistant/message embeds its source stream and cannot carry sourceEventSeqs`） |

两条合起来就是死结：**单条助手消息本身改不了**——要替换它就得带来源列表，带了就抛错，不带就覆盖不全也抛错。宿主有意不让改写模型自己发出的那条消息（原话"embeds its source stream"）。

**但把「调用 + 它的返回」两条一起换掉是合法的**，这也是现在采用的解法（`foldCallRecord`，默认开）：

| 环节 | 做法 | 为什么 |
|---|---|---|
| 时机 | **下一次 `agent/pre-step`**，不在工具里当场做 | 工具返回那一刻宿主还没追加 `tool/result`；只删调用会留下孤儿返回 |
| 范围 | 只认「带我们 `callId` 的那条助手消息 + **它自己**那条返回」，两者按 `callId` 认、不按下标假设相邻 | 并行调用时返回可能乱序到达；用 `session.log` + `deriveEventMessage` 逐节点问"这个节点是哪条消息"，才能在空节点、乱序里定位。**注意"并行"指同一条消息里有多个调用，不是一轮里调了多次工具**——一轮里连调三次工具是三条消息，照折不误（`plugin/lib/callfold.js:131-151`） |
| 产物 | 一条 `user/message` 短注：调过 compress、成功了、压了什么；**不提任何工具名** | 新事件不是 `assistant/message`，就不触发那条禁令；两个被遮节点全在来源列表里。提工具名会诱导模型"去看一眼"，而地图只给标题、不给摘要正文，那趟纯属白花 token |
| **并行降级**（2026-10-30 P0-2，2026-10-30 晚按用户裁定改） | 同一条助手消息里还有别的调用 → **不整段替换**，只把那条 `tool/result` 的正文折成「每个键的结果 + 一句『（地图已折叠：要接着压就重新调一次 context_map 拿新地图。）』+ 一句『这次 compress 是和别的工具一起并行发的：以后请把它单独发成一条消息——并行时摘要正文会以调用参数的形式一直留在上下文里（删不掉），白占一份钱。』」，并销掉待折项 | 整段替换会带走兄弟调用、让它变成孤儿（宿主不清洗孤儿 → 此后每个请求 400）。**地图必须折掉**（每次 500–700 token）；**每个键的结果必须留**（压了哪几层、省了多少，是模型决定下一步压什么、以及知不知道自己已经压过的唯一依据）；**并行这件事必须当场说清**，因为这条回执是模型唯一能读到"别再并行"的地方（系统提示那句可能已经被它跳过）。代价写在下表：`summary` 参数那份副本省不掉，要等后续压缩把它遮蔽 |
| 失败回执 | 末尾返回以「没能压缩：」开头 → 只把地图换成一句「（地图已折叠：需要时重新取一次地图。错误原因保留在这一条里。）」，**错误原因逐字保留** | 失败回执每次重试都会多一张 400–700 token 的地图；但原因必须留着，否则模型不知道错哪、为什么错（m11021） |
| 失败 | 返回对不上 / **两张表数量不等且找不到精确映射** / 返回是 `isError` / 开关关掉 → 一个字节都不动，原样留着 | 宁可多花 token，也不制造孤儿、更不换错节点 |
| 失败被看见 | 写日志 + **在 `/context-status` 末尾打一行「折叠上一次失败（时间 + 原因）」**；那一条待折项当场丢掉（`plugin\index.js` 的 `FOLD_REASON_TEXT` 把 `error-result` / `node-unknown` 翻成人话） | 这一项原先只写日志文件，插件表面上一切正常、只是白花 token；用户明确要求不要静默吞。**丢掉就不会再补折**：那对节点已经被后续消息顶离尾部，重试也不会成功 |

**`messages` 的下标不是节点身份**（2026-10-29 复审抓到的 P0）：`surface.nodes` 与 `deriveMessages()` 一般一一对应，但宿主会**跳过内容为空的 `system`/`developer`/`assistant` 消息**（`dsh-session:222-226` 返回 `null` → `:1681-1684` 只 push 非空项）。一旦表层里有这种节点，两张表就差一格，拿 `messages` 的下标去取 `nodes[下标]` 会**替换到别的节点**、并把真正那条留成孤儿。所以折叠**不靠下标对齐**：精确路径用 `session.log[seq]` + `session.deriveEventMessage(event)` 逐节点问"这个节点是哪条消息"，按 `callId` 认调用与它自己的返回（`plugin\lib\callfold.js` 的 `messageAtNode` / `locateCall`）；只有宿主收缩到没有这两个入口、且 `messages.length === nodes.length` 时才退回按下标，数量不等就整条放弃。这与"位置不是身份"是同一个错误换了个外形。
| 生效点 | `pre-step` 在下一次请求之前，所以那份参数副本**不会再被发出去一次** | 省下的是整份参数，不是"下次压缩时" |

**为什么只能在 `pre-step`，不能在工具里当场折**（2026-10-29 读宿主源码确认，三条例证）：

| 事实 | 出处 |
|---|---|
| `tool/result` 是 step 收尾时由 agent loop 同步 append 的 | `app.asar\dsh\node_modules\@deepseek-ai\dsh-agent-loop\lib\index.js:571` → `:697`（`session.append("tool/result", {` / `surfaceOp: "append"`） |
| 下一次 `pre-step` 在**下一个 step** 开头触发，中间只隔 `step/end` 与一次 `assemble` await | 同文件 `:953-1008` 主循环；`:909` `await this.dispatch.waterfall("agent/pre-step", {`；`:907` `await this.loopCtx.systemPrompt.assemble(...)` |
| **不允许在一次 append 的发布过程中再 append** | `dsh-session\lib\index.js:1570` `session append cannot reenter while another append is being published` |

所以"在事件回调里顺手折一下"这条路被宿主明确堵死；而工具执行时它自己的结果还不存在。`pre-step` 是**最早合法的落点**，且它仍在本次请求发出之前。

**"那就干脆少删一条 / 不返回结果"也堵死了**（2026-10-29 三包只读核查，`orphan|sanitize|pair|balance` 零命中）：

| 事实 | 出处 |
|---|---|
| 请求里的消息就是 `deriveMessages()` 的逐节点投影，**没有任何配对清洗**，孤儿 `tool/result` 会原样进请求 | `dsh-agent-loop\lib\index.js:1274`；`dsh-session\lib\index.js:1672-1687`；`dsh-session\lib\index.js:227`（`case "tool/result": return event.data.message;`） |
| LLM 层唯一的消息过滤只管 `developer`，工具结果直通适配器 | `dsh-llm\lib\index.js:756`；`dsh-llm-deepseek\lib\index.js:1689-1693` |
| 写结果无条件、也不校验调用是否还在表层 | `dsh-agent-loop\lib\index.js:571`、`:691-707`；`executeToolCalls` `:506-533` |
| 工具**无法**让宿主跳过这一行：正常/空内容/抛异常/被取消/step 抛错 **全部**落 `tool/result`；`silent\|hidden\|noSurface` 零命中；`presentationMeta` 只影响展示 | `:528`、`:984`、`dsh-tools\lib\index.js:3440-3444`、`:2977` |
| 宿主自带的 repair 只做反方向：给"有调用没结果"补合成错误结果（`TOOL_NOT_STARTED` / `TOOL_OUTCOME_UNKNOWN`），**从不删孤儿**，也不在请求前跑 | `dsh-session\lib\index.js:718-897`（`openTurnClosers`:750、`ToolCallRecovery`:804-897） |

**因此"必须成对才折"不是卫生习惯，是安全边界**：一旦只删调用、留下结果，这条会话会带着一条对不上 `tool_use` 的 `tool_result` 一直坏下去。省下的 token 与"工具内当场删"完全相同——两份副本从未进入任何一次请求。

**用户插话不会打乱折叠**（2026-10-29 只读核查，`dsh-api-session-controller` / `dsh-agent-loop` / `dsh-session`）：

| 事实 | 出处 |
|---|---|
| 插话先落**持久化收件箱**，此刻不产生任何 `user/message` | `dsh-api-session-controller\lib\index.js:925` `async prompt(request, source)`；`:949-950` `if (request.mode === "steer") agent.steer(message); else agent.followup(message);` → `dsh-agent-loop\lib\index.js:803` `this.inbox.splice(...)`；`:810` steer 目标 `"next-step"`、`:807` followup `"next-turn"` |
| 落成表层节点发生在 `step()` 内部、**在 `agent/pre-step` 之后** | 同文件 `:1072` `} else this.session.append("user/message", message, { surfaceOp: "append" });`；claim `:906`、waterfall `:909` |
| 工具执行期间到达的插话只写收件箱，**不会插进 `tool/call` 与 `tool/result` 之间**；表层顺序取 `surface.nodes`，不是原始日志顺序 | `executeToolCalls` `:506`；结果写于 `:571` `appendToolResult(...)`；`dsh-session\lib\index.js:1674` `const nodes = surface.nodes;` |
| **没有"插话打断工具"的机制**；只有 `cancel()` 会 abort，且已启动的工具照写正常结果，未启动的写 `TOOL_ABORTED_BEFORE_DISPATCH`（`isError: true`） | `:855-857`（running 时只置 `wakeRequested`）、`:820`、`:632`（排空 inFlight 才进 aborted 分支）、`:668` |

结论：`pre-step` 时刻末尾**必然是"助手消息 + 它的返回"**，插话只会在折叠之后才落上一行，因此折叠在时序上不会认错节点。两条附带事实：①若 `pre-step` 派发时 `signal.throwIfAborted()` 抛错，被 claim 的插话**既不回收件箱也不落表层**（`dsh-agent\lib\index.js:56-58` 注释自认，`dsh-agent-loop:104` 的 `discardRemoved=false`）；②原始日志里 `agent/inbox/spliced` 确实可能夹在 `tool/call` 与 `tool/result` 之间——**这正是"不读日志、只看表层"的又一条理由**。

**正文文本零清洗**：`deriveMessages()`（`dsh-session\lib\index.js:1672-1687`）逐节点投影、`case "user/message": return event.data;`（`:221`），append 只做 `snapshotJsonValue`（`:1523`）与 `state.nodes.push(plan.seq)`（`:464`），**不做转义、截断或改写**——块正文里的 `T16–T19`、`〔〕`、`｜` 原样进请求。

**"在 `agent/pre-step` 里写会话"是宿主明确允许的，不是灰区**——宿主自己的 `compaction-basic` 就这么做，而且在里面完成整个压缩事务（三个日志事件 + 一次表层替换 + 一次摘要请求，全部 `await`）：

```js
ctx.on("agent/pre-step", async ({ agent, signal }, next) => {      // dsh-compaction-basic\lib\index.js:839
  if (!signal.aborted) try {
    const result = await this.compactIfNeeded(agent, "pressure", signal);  // :841
    ...
  } catch (error) { /* 记录后继续这一轮 */ }                        // :843-850
  return next();                                                    // :851
});
```

由此得到三条必须照抄的纪律（我们的 `plugin\index.js:147-153` 已符合）：

| 纪律 | 原因 |
|---|---|
| 在 `next()` **之前**做完 | 之后再做，结果要等下一轮才生效；`compaction-basic` 也是先做完再 `next()` |
| 异常必须**吞掉**，绝不穿透 | 穿透会让整个 step 失败；`compaction-basic` 捕获后打日志再 `return next()`。**更糟的是这错会被静默吞掉**：`cordis/src/events.ts:234-243` 的 waterfall 全程无 try/catch，异常冒泡到 `dsh-agent-loop:1010` 的 `throwError`，再被 `:887-901` `kick()` 的 `catch (_error) {}` 吃掉 —— 表现是**这一轮不再发任何请求、用户看不到任何原因**。所以 `pre-step` 与 `request-error` 两个 handler 的整个函数体都包在 try/catch 里（`plugin\index.js`） |
| 只做一次同步表层写入 | 一次性替换不会留下"写了一半"的中间态；`append` 的重入护栏（`dsh-session:1570`）只在"另一个 append 正在发布"时才拦，`pre-step` 时没有 append 在进行，所以合法 |

**折叠失效时的排查顺序**（按可能性）：① 有别的插件也挂 `agent/pre-step` 且在我们之前往表层追加了消息 → 尾部那一对不再相邻，折叠静默跳过；② `tools/post-execute` 换掉了结果内容 → 内容变了但相邻性不变，不影响；③ 模型在同一条消息里发了多个工具调用 → 按设计放弃；④ 开关 `foldCallRecord` 关着。前三种都只多花 token，不坏会话。

**折叠失败不再只躺在日志里**（2026-10-29 用户要求）：`foldPending` 抛错时把 `{at, error}` 记在队列对象上，`/context-status` 末尾追加一行；同一份待折项保留一次、下一次 `pre-step` 再试一次，第二次仍失败才丢弃并清空队列（`plugin\index.js` 的 `queue.failures`/`queue.lastError`）。成功折叠会清掉这两项。丢弃之后**不会再补折**——那对节点早已被后续消息顶离尾部，任何"补折"都得改写历史中段，那是另一套机制，本版不做。

**折叠按"节点号"定位，不按消息下标**（2026-10-29 终审发现的问题）：宿主会跳过派生为空的节点（`ref/upstream/session-index.ts:1008-1019` 的 `if (msg) this.derived.push(msg)`），只要会话里出现过一个空节点，`deriveMessages().length !== surface.nodes.length` 就恒成立。旧实现拿"数量必须相等"当一票否决，结果是折叠（默认开）**永久静默失效**：`compress` 的完整参数与返回一直留在上下文里，`/context-status` 与日志里都没有记录，而且 `foldPending` 还把 `note === null` 当成功、把失败计数清零。

现在改成：`rememberFold` 时用 `callNodeOf(session)` 记下调用落在哪个节点上（工具执行那一刻，`tool/result` 还没追加，调用消息就是最后一个节点），折叠时 `nodes.indexOf(callSeq)` 精确落位；只有拿不到记录且数量相等时才退回按下标。折不掉时**不再装成功**：`foldCallRecordEx` 返回 `{note, reason}`，`foldPending` 把 `error-result` / `node-unknown` 记进 `queue.lastError`（`/context-status` 显示）、并把那一条丢掉，不每轮白撞。

**折叠不再打废地图**：折叠本身是一次 `replace`（`replaceGeneration + 1`），会让刚续上的地图许可证失效，于是"压完一层想再压一层"必被假报"地图过期"。现在折叠成功后调 `license.restate(agentId, session)` 把代数对齐——折叠只动尾部那一对，区序号、块顺序、轮号都没变。

另一条被纠正的猜测：子 agent 完成、后台任务完成、goal 续作这类通知**不会插在工具结果与 `pre-step` 之间**——它们先进 durable inbox（`agent/inbox/spliced`），到 step admission（`pre-step` 之后、请求之前）才落成 `user/message`。因此在 `pre-step` 那一刻，compress 的调用与结果是**必然相邻的一对**。

`callId` 不是跨消息的身份（2026-10-29 复审抓到）：宿主只保证**同一条助手消息内**不重号，跨消息可以复用。若上一次成功登记了待折项却没折成（比如那条消息里还有别的调用），队列里就留着旧记录；随后一次同 id 的调用**失败**时，`isError` 未必为真（失败文本也是正常返回），下一次 `pre-step` 就会拿旧记录把失败折成「已经成功」。因此每次 `compress` **一开始**先 `forgetFold(queue, exec.callId)` 作废旧待折项（`plugin\index.js`），成功时再登记。宁可少折一次，不可把失败写成成功。

代价：模型看不到那次调用的完整返回，只剩一句摘要式回执（截断说明在面板「折叠压缩调用记录」里有写）。`segment.*` 与压缩频率这两条老路仍然有效。

## 9. 提醒

插件往对话尾部追加文字，三种触发，互相独立：

| 触发 | 频率 | 文案要点 |
|---|---|---|
| 占用 ≥ `triggerPct`（0.75） | 每轮一条（同一轮多步只发一条） | 说明式（**不是命令式**，m08640）：现在可以压、位置在下面这张地图里；附当前地图；第二次起因"上次压完仍高于线"换说法 |
| 自上次提醒后又长了 `notice.growthTokens`（65000） | 每触发一次发一条 | 写 **0 表示关闭这条触发**（只在到线时提醒）；能写 0 但不能写负数 |
| 某层区超 `budget.*` | 每层首次越线发一条，回落复位 | 说清前提：超的是哪区、要压就得连下面几层一起压 |

**投递时机（2026-10-30，用户 m10194 定）**：检测是每步一次（挂在 `agent/pre-step` 上），但**提醒不在检测那一刻写表层**。命中后每一步只覆盖一条待发记录，收尾（`agent/turn-stopping`）时按**本轮同一个 `AbortSignal`** 把它认回来，然后走 `agent.followup(message)` 投递：消息进的是 inbox 的 `next-turn` 车道（`dsh-agent-loop/index.js:806-808` 的 `followup` → `send(…, "next-turn", true)`），宿主在本轮 `turn/end` 之后发现 inbox 有货就**立刻开新的一轮**（`:1037` `if (!this.inbox.hasPending) return false`），新轮第一步认领时由宿主自己写进表层（`:1072`）。

效果：**模型被叫醒后先压缩，用户的下一句话排在它后面**，不用等用户开口。提醒内容里带**完整地图**（块表 + 压缩须知 + 占用），模型不必再单独调 `context_map`。

**提醒、拒绝回执、成功回执三处都必须带完整地图**（2026-10-30 用户两次驳回"紧凑版"改动）：完整地图 = 块表（标题 / 覆盖轮次 / 每块 token）+ 每层压力与配额（含"占可用输入"百分比）+ 可压区间 + 压缩须知（含**级联要求**一行：压 l1/l2/l3 时比它浅、且还能压的层要同批一起给，2026-10-30 补——之前地图只给位置不说级联，模型照图只给 l1 会整批被拒）。这三处恰好都是"模型马上要填 `to`"的时刻——
- **提醒**：靠块标题与块大小决定并哪几块、压完会不会更大；
- **拒绝回执**：`错误原因 + 地图`，模型才知道错在哪、为什么错，而不是再撞一次；
- **成功回执**：刷新后的地图让"压完接着压"不必再单独调 `context_map`（`ae398aa` 起的行为约定）。**它会被折叠，但地图不会丢**：`foldCallRecord` 把"compress 调用 + 它这条结果"两条节点换成一条 `user/message`，内容 = 每个键一行结果 +（剪过才有的）剪枝那行 + **刷新后的完整地图** + 一句"已折叠"。所以模型真正看到的是这条折叠记录，地图就在里面（多行的地图原样贴、不加 `- ` 前缀，块表要对齐；`plugin/lib/callfold.js` 的 `buildNote`）。**原设计稿没有规定"成功之后留什么"**：`notes/2026-10-27-DSH原生分层压缩-设计方案.md:2244` 只写"`compress` 成功回执（每键一行）或失败原因"，`:787` 写"压缩后的占用回报默认走工具结果的 `render()` 卡片，**不额外占一个消息节点**"。折叠是本版实现时后加的机制，理由是"摘要正文已经作为块存在，别再在调用参数里存第二份"（见 §7）。

设计依据是原始设计稿（`notes/2026-10-27-DSH原生分层压缩-设计方案.md:99`「提醒里直接带地图」、`:266` 的地图样张「每层压力 + 每段内容标题」、`:293-294` 的"地图给索引与压力，不是内容替代品""地图必调"）。**代价（450–690 token/次）是设计上认过的账，不许再用"省 token"当理由改成一行数字。** `plugin/test/prestep.test.mjs` 有一条断言钉住提醒里必须出现"压缩须知"、且不得出现旧的紧凑版标记串；`plugin/test/map.test.mjs`（8 项）钉住地图的三样东西——每层压力（已用/区上限/单块上限）、块表（序号+区+覆盖轮次+每块 token+标题）、可压位置与压缩须知。`renderBrief()` / `briefOf()` 已整个删除，防止有人重新启用。

> **教训（2026-10-30，写死）**：任何"给模型看"的文字（提醒、回执、地图、系统提示）要删要改之前，**先去翻设计稿与本节对应的条目**，逐条对过再动手；"省 token"不是理由，"单点成功率与轮次"才是设计目标。审核员只能查自洽，看不出这种偏离。

- **判定只算一次，收尾照单发**：`pre-step` 每一步都重算并覆盖那条记录（占用、增长、区超限），所以收尾拿到的是"最后一步看到的那份读数"——不在收尾再算一遍（用户 m10194 指出的重复）。后一步算出没理由了，就把记录撤掉，收尾不发。
- **区超限每轮扫一次**：结果存在 `st.zonesOver`，同轮各步复用，既省重复扫日志，也免得同一条提醒在几步之间理由来回变。**回落要复位**：某区掉回线下时把 `st.zones[key]` 置回 `false`，否则这个会话里那个区报过一次就再也不报了（只压某一层的工作流里，压小后再次越线会彻底静默）。
- **记账在投递成功之后**（`commit()`）：先记账会让"发送失败"也算发过，于是这一轮白算、下一轮又登记又失败、区越线标志还被白白置位。
- **压缩成功后要把增长基线重置**（`resetGrowthBaseline`，`plugin/index.js`）：增长触发比的是"自上次提醒后又长了多少"，而 `commit()` 记的是**压缩前**的用量。压缩成功如果不重设基线，基线就永远停在压缩前的高位，`grew` 长期是负数，`notice.growthTokens` 这条触发等于关闭（终检 2026-10-30 抓到的"静默失效"之一）。
- **认不出块的状态不叫醒**：`st.ambiguous`（映射拿不到 + 已有块）为真时只 `forgetPending` 后返回——叫醒了也压不动，每轮白烧一次请求与一次失败调用的 token，最后把人逼去 `/compact`。
- **只叫醒一轮**：被叫醒的那一轮（`st.autoTurn === turn`）不再登记第二条——既不再叫醒，也不重复发同一句话。否则模型"读了提醒什么也没压"会让每一轮都再叫醒一次，连环烧钱。用户真开口（`pre-step` 第 1 步认领到的消息里有一条不是我们的 `ebbing-context-notice`）就复位，下一次收尾仍可再叫醒。这是唯一一道刹车，**不是配置项**：它是"别把同一句话说两遍"的硬约束，不是调参面板上的旋钮。
- **拿不到活 agent（没有 `followup`）**：退化成尾部追加。
- `agent/turn-stopping` 只在正常收尾时触发（`dsh-agent-loop/index.js:1001`，条件是 `turnEnds && inbox.nextStep.length === 0`）。**派发点写的是字面量 `{ turn, signal }`，但收件人拿到的载荷里一定有 `agent`**：`this.dispatch` 是 `agentEvents(loopCtx, this)`（`dsh-agent-loop/index.js:777`），它的 `emit`/`waterfall` 都先过 `fused(payload) = { ...payload, agent }`（`ref/pkg-0.2.1-rc.3/dsh-agent-index.js:242-246`、`:268-270`；`agent` 就是那个 `AgentLoop` 实例本身，所以能直接调 `agent.followup`）。待发记录仍按 `signal` 登记——信号是本轮的身份（`turn()` 每轮新建一个 `AbortController`，`dsh-agent-loop/index.js:1038`；`pre-step` 与 `turn-stopping` 取的都是 `this.phase.abort.signal`，`:905` / `:1003`），比 agentId 更精确（同一 agent 上一轮的记录不会串到下一轮）。
- 本轮以异常/取消收场时 `turn-stopping` 不会来，那条记录的信号已经作废：**直接丢弃，不补发**（补发就是拿过期读数说话），交给下一步重新判一次。
- 提醒只是催，**不保证模型会压**。
- 掉到 `triggerPct` 以下不重置"已经提醒过"的记录，下一轮达到线继续提醒（没有滞回）。
- `agent/request-error` 的超限通知**不走这条路**：那是检测到就即时追加的（见 §10）。

## 10. 超限

`agent/request-error` 命中 `CONTEXT_WINDOW_EXCEEDED_CODE` 时：先 `ctx.goals.disarm(agent)` 摘掉自动续作权限，再追加一句面向人的通知。通知里**不催 `/compact`**（用户 m08342：那是不可逆拍平）：先说清 `compress` 此刻调不动（它依附在一次成功的请求上），让用户去调 `maxTokens` 或换更大窗口，要不要用宿主压缩由用户自己决定。**不自动压缩、不重试、不改写历史。** 非本码立即 `next()`。

## 11. 取回

压缩掉的原文仍在会话日志里。取回**全部委托宿主**：`session_event_search`（`surfaces:["shadowed"]`）+ `session_event_read` 按事件号读原文。插件自己不实现取回工具。

因此：**每次工具调用时**检查这两个工具在不在（`plugin/index.js` 的 `missingSessionQuery()`，不缓存判定）；不在就 `compress` / `context_map` 都返回"请开启 DSH 的实验性插件：会话搜索"，且不做任何写入。启动即报错会拒掉整个插件，装配顺序稍慢半步就白屏，所以改成调用时判。

title:    { maxTokens: 50 }
triggerPct: 0.75

notice:   { enabled: true, growthTokens: 65000 }
requireSessionQuery: true
pruneFirst: true                                   // 剪大工具返回：只在每次压缩前剪一次

**这 15 个叶子（budget 3 / segment 3 / title 1 / notice 2 / triggerPct / keepTurns / pruneFirst / foldCallRecord / requireSessionQuery / reservedTokens）必须全部出现在宿主的 `Config` schema 里、并且逐个 `.volatile()`。** 只写进 `DEFAULTS` 与 `validateConfig` 是不够的：宿主按 schema 解析配置，schema 里没有的键会被丢掉或拒绝，面板与 YAML 改了都不生效——`keepTurns` 就曾漏了 schema 而永远停在 2（`e15ec16` 补上）。

长度一律用**插件自带的估算器**（中日韩 1 字=1 token，其他非 ASCII 1，ASCII 数字 3 位=1，ASCII 其他 4 个=1），不用宿主的 `CHARS_PER_TOKEN=4`——它对中文低估约 4 倍。

## 13. `compress` 的处理顺序

1. 许可证检查 → 2. 参数形状（四个键、`to` 的类型、`title`/`summary` 的长度）→ 3. `pruneFirst`：`ctx.get('toolResultPruner')?.pruneSession(session)`（报 `prunedChars`；宿主的剪枝是**全局服务**：任何工具返回超过 `thresholdChars` 8192 字符就挖掉中间、留头 4096 + 尾 1024，只改 `tool/result`，碰不到 `assistant/message` 与 `user/message` ⇒ 压缩块与摘要剪不到）。同一个 pruner 只有这一个调用点：宿主自己只在它的自动压缩（context-overflow / pressure）里叫它，我们的 `auto` 关着，所以整个世界只有"我们要压缩了"这一刻会剪——**这与宿主的语义同构**：宿主也把剪枝当作压缩的前置步骤（pressure 越过阈值才调，剪完若已低于阈值连压缩都不做）。不在每步请求前剪（设计裁定，用户 m13359）：那样会在任意步削掉模型正要引用的内容，而剪掉的中间段不一定取得回（没装会话搜索时两个工具是停用的，剪枝却不受那道闸门约束）。→ 4. 读区与算层级 → 5. 逐个键解析 `to` 并建区间（其中含"这层还能压"的判据、区间纯度、边界安全、长度与标题校验）→ 6. 区间两两不相交 → 7. **级联校验**（缺层则整批拒绝，并在拒绝语里给出可写的 `to` 范围）→ 8. 全批**预演**（`commitOne(..., dry)`，不落盘，先确认每个键都合法）→ 9. 按表层位置升序逐个子事务落盘（`try/finally` 保证补 `end`）→ 10. 返回结果（每个子事务的块位置、盖掉的条数、省下的 token，以及总量）→ 11. 成功时把本次结果登记为"待折叠"，由**下一次 `agent/pre-step`** 把「这条调用 + 它的返回」一起换成一句短注（`foldCallRecord`，见 §7）。

**多键批失败时要说清落在哪一步**：预演阶段失败则"一条都没写"；落盘阶段失败则把 `result.partial` 里已经写进去的层名列出来（`plugin/index.js` 读 `partial`，不是 `results`）——否则模型会整批重发，把已写的层再压一遍。

## 16. 卸载之后会留下什么

结论：**可以无损卸载，有三种残留，但都不会让会话坏掉**。

插件注册的东西全部挂在 `ctx.effect` / `ctx.on` 上：两个工具、一段系统提示、**五个事件监听**（`agent/pre-step`、`agent/turn-stopping`、`agent/request-error`、`agent/disposed`、`loader/volatile-update`）、一个 `/context-status` 命令。卸载即撤销，不留任何挂在宿主上的钩子。

其中 `agent/turn-stopping` 只做一件事：把本轮攒下的那条提醒在收尾时发出去（见 §9 的投递时机）。派发点的字面量只有 `{ turn, signal }`，但 `agentEvents` 会给每个 agent 事件的载荷补上 `agent`（`ref/pkg-0.2.1-rc.3/dsh-agent-index.js:242-246`），所以收件人手里是有活 agent 的；待发记录仍按 `signal` 登记（`WeakMap<AbortSignal, record>`；另有一张 `Map<agentId, {signal, record}>` 只用于清理异常收场留下的孤儿），因为信号才是本轮的身份。投递走 `agent.followup()`。它是 `serial` 事件，宿主在同一位置还会写 `turn/end`，所以 handler 必须自己兜异常（抛出去会拦掉收尾流程）。

**`serial` 事件的监听器没有 `next` 参数（2026-10-30 真机故障的根因）。** 宿主用 `dispatch.serial(...)` 派发 `agent/turn-stopping`，监听器只收到载荷；写成 `(payload, next) => { … return next() }` 会在收尾阶段抛 `TypeError: next is not a function`，界面上的表现是「模型已经答完，却报 本轮运行失败」。只有 `waterfall` 事件（`agent/pre-step`、`agent/request-error`）才给 `next`。回归断言在 `plugin/test/prestep.test.mjs`：按真实派发方式只传一个参数调用 turn-stopping handler。

**`agent/pre-step` 是什么（别再窄化理解）**：它是宿主的**每步前置瀑布**，每一次请求构造之前都会跑一次（`dsh-agent-loop/index.js:908` 的 `await this.dispatch.waterfall("agent/pre-step", { messages: claimed, ...position, signal })`，`position = { turn, step }`）。宿主自己的 `dsh-compaction-basic` 就在这里压历史。我们借它做三件事：收上一次 compress 的调用记录（折叠）、判定要不要提醒、以及（`step === 1` 时）给被叫醒的那一轮复位闸门。它**不是**"压缩结束后删工具输出"的专用钩子——那只是折叠这一种用法。

`pre-step` 是**被 await 的**：我们算得慢，只会让这一步的请求晚一点发，不会和下一步抢跑、也不会丢事件。`turn-stopping` 是 `serial` 派发，同理。

**不注册 message projection、不注册 state projection、不写磁盘状态**——这是卸载安全的关键。宿主的规则是：缺少 message projection 会让旧会话拒绝继续派生，所以那类东西一旦注册就绑死了会话生命周期。我们不碰它。

留在会话里的三种东西：

| 残留 | 形态 | 卸载后表现 |
|---|---|---|
| 压缩块 | 一条普通 `user/message`，正文第一行自带 `〔L1｜T16–T19｜ev …〕` 元信息 | 照常显示、照常被模型读到；没有插件也能看懂它是压缩结果 |
| 四条记录 | `compaction/start` / `summary` / `end` + 替换消息 | 都是宿主本来就认识的类型；未配对只会影响宿主的压缩锁 |
| 提醒与超限提示 | 普通 `user/message` | 就是一句历史消息，无害 |

**唯一的真实风险**：条写在同一段同步代码里，中间被进程强杀会留下未配对的 `compaction/start`。宿主据此认为"会话里已经有压缩在跑"，此后 `/compact` 与宿主自动压缩都会被拒（报 `compaction already in progress`），直到这次会话生命周期出现新的 `session/end-seed`（重启会话即可）。普通异常走 `try/finally` 已经覆盖，剩下的只有强杀这一种。

## 17. 插件自己的记录：没有任何会单调增长的东西

| 记录 | 存在哪 | 是否随会话增长 |
|---|---|---|
| 压缩块的层级 / 覆盖轮次 / 事件号 | **写在块正文第一行**，不是我们的表 | 否（块数受 `budget.*` 约束；L3 可多块） |
| 图片台账 | 块正文**末行**：`〔这块压掉了 N 张图片（事件号 …）。需要看图时用会话搜索按事件号查看。〕`；只在被压区间里真有图片时写 | 否（N 与事件号都是写入时算死的快照） |
| 轮号 → seq | 读宿主 `turnOutline` 投影，只读不写 | 否（宿主自己的账） |
| 提醒去重（`reminded`） | 进程内 Map，按 agent 存 | 否（`agent/disposed` 时删除） |
| 超限去重（`overflowSaid`） | 同上 | 否（同上） |
| 运行日志 | `<DSH_HOME>/logs/ebbing-context.log` | 是，所以**按大小滚动**：2 MiB × 2 份，单条 ≤4 KiB，写失败静默 |
| 配置校验状态（`Config`） | 已实现：宿主 schema + 自带 `validateConfig()` 双保险 | — |

设计上刻意不用 projection 台账：块自己带着元信息，插件随时可以从表层重建全部状态，**重启、换机、卸载后的行为完全一致**。

### 19.1 拒压的容错预算（2026-10-29 用户提，待拍板）

用户原话（m08342）：*"我依旧严重怀疑这一块会使得我们插件频繁报错导致用户不得不 /compact 毁掉整个历史，这是不可接受的。"*

风险链：**拒绝 → 模型重试（每次都花 token 读地图）→ 连续失败 → 用户认为插件坏了 → 手动 `/compact` → 宿主八段式摘要把金字塔拍平，且不可恢复**。

现在有 8 种"整批拒绝"（§18 表），其中三种是"模型自己填错"（可以从地图抄对），五种是"环境/设计约束"（模型再试也没用）。**没有区分这两类**——对后者反复重试纯属烧钱。

候选改法（按代价从低到高）：
1. **拒绝要能自愈**：凡是"这次不行、改一处就行"的，返回值里直接给出改好的完整参数（例如"把 `to` 从 `T19` 改成 `T16` 即可"），而不是只描述错误。
2. **同一会话连续 N 次拒绝后降低门槛**：把"最低收益"从"必须比被压内容小"放宽到"允许净增不超过 X%"，宁可少省一点也别让用户去敲 `/compact`。
3. **降级通道**：级联缺层被拒时，允许"只压最顶层的那一层"作为最低限度的保底（只保留金字塔形状，不追求省 token）。
4. **明确告诉用户别敲 `/compact`**：拒绝信息里加一句"这不是坏了，可以换 `l1`/`l2` 试试；宿主自带的 `/compact` 会把分层拍平，请勿使用"。

第 1、4 条不改设计语义，可以随时做；第 2、3 条会动"唯一硬约束是压完必须更小"，需要用户拍板。

**本轮已顺手拆掉其中一个死锁**：级联的判据从"这层还有内容"改成"这层还能压"（`canCompressZone()`）。原来某层只剩 1 块时（最后一块按新规则不压），级联会一直要求它一起压，于是整批永远过不去——那正是"用户被逼去敲 `/compact`"的标准场景。

### 设计级死锁（需拍板，不是 bug）

硬级联 + 逐键收益校验会互相锁死：

> L3 区有大量可缩内容，但 L0 只剩一条已结束的短确认（例如"好"）。级联要求同批必须给 `l0`；新 L1 块的固定开销（块头 + 宿主前导语 + 取回线索）远大于这一点原文，收益校验因此拒绝整批 —— **连 L3 也压不了**。

反方向同样成立：提醒要求"从最高非空层开始"，若该层已经短到无法再缩，即使 L0 能省很多，整批也失败。

候选改法（都会改设计目标，不是实现小修）：
1. 级联改成"批次总收益为正"而不是逐键收益；

### 20.2 三条被澄清的设计前提（写代码前先对照）

1. **一次提交 = 一次执行。** 模型把 `l2 to n`、`l1 to m`、`l0 to x` 写在**同一个工具调用**里；插件在一次执行内把受影响的层全部改完。不存在"压一层执行一次"，这是前缀缓存的决定性约束：要动深层就必须把所有受影响层一起动，一次断点。插件全程不调用模型。
2. **判定必须全部前置。** 宿主没有事务，`append` 不可撤销。所以"验一层写一层"会让第三层的不合格发生在第一层已落盘之后。规矩：全部判定跑完、全部通过，才开始写；写的过程中不再做判定。
3. **不需要虚拟表层。** 曾经需要，唯一原因是 `l2` 产物要拼接旧 L3 正文，从而依赖"L3 被压之后的样子"。`849368c` 去掉拼接后，各层产物互不依赖，区间又都按事件号（不是下标）定位，因此"先在假表层上推演"没有额外好处，予以取消。

**轮次归属按表层下标，不按事件号（2026-10-29 追加）。** 宿主在 pruner 剪枝时做的是**原位替换**：替换事件拿到一个新的、更靠后的事件号，但它在表层上仍是原来的位置。若按事件号比大小判轮，旧轮的工具结果会被算进当前轮，`l0 to=T1` 的区间就会漏掉它，配对检查随之失败（该压的压不动）。因此轮次归属改为：先把每个轮首事件号映射成它在 `surface.nodes` 里的下标，再按节点下标判轮；只有轮首本身也被替换掉（取不到下标）时，才退回按事件号比较。对应断言测试：`plugin/test/blocks.test.mjs`。

**图片离线化不是原位替换（2026-10-29 审核员复核更正）。** 它是 **message 投影**：只记一条"省略最老图片"的决定，在派生消息时生效，`surface.nodes` 与事件号都不变（`dsh-compaction-image-offload/lib/index.js:97-120`）。因此它既不与折叠争旧 seq，也不影响按下标判轮——上面那段只说 pruner。

**地图分母与提醒线同源（2026-10-29 追加）。** 地图展示的"可用输入"必须用与 `readUsage` 完全相同的预算公式 `max(floor(窗口×0.1), 窗口−输出预留)`，不能直接写 `窗口−预留`。否则 `reservedTokens` 配得离谱时会出现"占用 40% 却显示分母 5000"这种自相矛盾的展示；下限钳制同时保证分母不会变成 0。

**修正：轮次界标不能用 turn/start 的事件号（2026-10-29）。** `turnOutline` 投影里的 `turns[].seq` 是 `turn/start` 事件的事件号，而 `turn/start` 只进日志、不是表层节点（`SURFACE_EVENT_TYPES` 里没有它），所以拿它去 `surface.nodes` 里查下标永远查不到、会静默退回按事件号比较，整条修复等于没生效。正确做法：取"该轮 `turn/start` 事件号之后**第一个出现在表层上的节点**"（那才是这一轮的 user 消息）作为该轮的界标，再用它的下标判轮。断言测试已改为真实契约（轮首事件号 9 / 49 不在 `surface.nodes` 里）。

**空节点不再让会话永久压不动（2026-10-29 追加）。** 宿主在 `deriveMessages()` 里会跳过"派生为空"的节点（被 `max_tokens` 截断的空助手消息、空的注入消息，见 `ref/upstream/session-index.ts:1008-1019` 与 `ref/upstream/session-surface.ts:135-142` 的逐字注释）。旧实现一见 `消息数 ≠ 节点数` 就整批拒绝，于是一次截断就永久废掉这条会话的压缩能力。现在的规则：
- **首选：逐个节点投影**（2026-10-30 补，取代下面那条"数量不等就没辙"的判断）。宿主没有任何一条规则不让我们问——`session.log` 是公开字段（`ref/pkg-0.2.1-rc.3/dsh-session/index.js:504` 声明、`:519` 赋值）、`session.deriveEventMessage(event)` 是公开方法（`:555`、`:1694`）。于是 `plugin/lib/blocks.js` 的 `deriveExactly(session, nodes)` 对每个节点调一次，得到 `seq → message | null` 的精确映射；`messageFor(seq)` 再把它包装成"按节点取消息"。映射在手时：空节点（映射为 `null`）被跳过、块照旧按块头识别、区间与配对（`checkPairing(zones, …)`）全部按节点算——**块起点不再需要整轮边界那条粗判据**，`isTurnBoundaryPair` 只作兜底。
- **兜底：数量不等且映射拿不到**：放弃消息下标，改判**区间两端是否落在整轮边界上**。完整轮次内部的工具调用与结果天然成对（宿主不会让一轮带着没答复的调用就结束，取消也会写一条 `isError` 的结果），因此这种区间不需要按消息复核；两端只要有一端切在轮中间，仍然拒绝并说明怎么挪 `to`。
- **判轮只依赖表层节点与轮次大纲**：轮首下标 = 该轮 `turn/start` 事件号之后第一个出现在表层上的节点的下标；轮末下标 = 下一轮轮首下标的前一个（最后一轮取表尾）。实现在 `plugin/lib/blocks.js` 的 `turnBounds()` / `isTurnBoundaryPair()`。
- **计价尺子也跟着降级**：只有映射拿不到、退回整轮边界时才没法按节点取原文，此时 `beforeOwn` 退回宿主口径、`afterOwn` 也用宿主口径——两侧仍是同一把尺子，不做一边宿主一边自研的比较（那正是审核员抓过的"第二把尺子"）。映射在手时照旧用自研口径（`ownTokens(live, …)` 内部走 `messageFor`）。
- **地图会说明这件事**：空节点数 > 0 时地图多一行提示，避免"节点数≠消息数"看起来像 bug。
- 顺带的自愈：被压掉的区间里若含空节点，它们随替换一起消失，下一次 `消息数` 就追平了。
- 对应断言测试：`plugin/test/blocks.test.mjs`（整轮边界的放行/拦截/null 三态）。

## 21. 配置界面（浏览器侧，2026-10-29 新增）

### 21.1 面板位置

配置表单不属于「设置」页：**「设置」里的插件清单是只读的**，可写的配置页在**侧栏「插件」面板**里，挂在 bundle 详情页上（`@deepseek-ai/dsh-client-ui-plugin-manager/README.md:14`、`:73`）。

三种槽位（同一份 README `:73`）：

| 槽位 | 用途 | key |
|---|---|---|
| `plugins.item` | 官方插件自己的配置页 | 入口 id |
| `plugins.bundle.config` | **整个 bundle 的配置页**，渲染在描述与行列表之间 | **包名** |
| `plugins.row.config` | 单行的配置页，注册后该行多一个 **Configure** 按钮 | `<包名>#<行 id>` |

我们用的是 **`plugins.row.config`**，key = `dsh-ebbing-context#dsh-ebbing-context`（`<包名>#<行 id>`，本插件两者同名）。

**为什么不用 `plugins.bundle.config`（2026-10-29 源码核实，曾写错）**：`PluginManagerPage.tsx` 渲染 bundle 详情页时传的是 `renderSlot('plugins.bundle.config', { view: 'page' }, { entryKey: pkg.name })`——**不带 `form`**；只有行详情页传 `renderSlot('plugins.row.config', { view: 'page', form }, { entryKey: rowConfigKey(pkg.name, row.rowId) })`，其中 `form = formFor(openRow.rowId)`，而 `formFor` 在 `configurations` 里没有该 `ns` 时返回 `undefined`。README `:131` 也写了「Bundle-wide pages can contain several entries and **have no single form**」。所以挂在 bundle 页上的组件拿不到 `form`，我们的 `draft` 只能一直显示「没有可编辑的配置」。

`formFor` 的完整实现（原文）：

```ts
const formFor = (id: string): ConfigPageForm | undefined => {
  if (!configurations?.some(view => view.ns === id)) return undefined
  const form = props.configForm<Record<string, unknown>>(id)
  return { state: form.getSnapshot(), mutate: (ops, revision) => form.mutate(ops, revision) }
}
```

⇒ 前提是**该行有 Config**（`ns` = 行 id），我们这行有。

**仅“有 Config”还不够（2026-10-29 补，P0）**：宿主只把**带 `volatile` 标记**的字段暴露成可编辑表单。`dsh-settings` 的 `volatileForm(schema)` 递归挑出 `meta.volatile` 字段，一个都没有就返回 `undefined`，于是该命名空间**根本不出现在 `configurations` 里** → `formFor` 返回 `undefined` → 我们的页面永远是“没有可编辑的配置”（写也会被拒：`Plugin entry ... has no volatile fields`）。

所以 `plugin/index.js` 的 `Config` 里每个叶子都加了 `.volatile()`（写法照 `dsh-better-sidebar/lib/index.js:121`：先构造完整 schema，再 `const volatilePrefs = ...map(([k, f]) => [k, f.volatile()])`）。**以后新增配置项，漏了 `.volatile()` 就等于这个开关在界面上不存在。**

另：槽位 `key` = `<包名>#<行 id>`，但 `formFor` 用的 `ns` **只有行 id**（`lib/client.js:27-29` 的 `rowConfigKey` 只用来拼槽位键）。本插件两者同名，所以看起来一样；将来改名必须分开处理。

### 21.2 宿主给的表单句柄（逐字契约）

页面渲染时传给注册组件的 owner props：

```ts
interface PluginConfigViewProps {
  readonly view: 'summary' | 'page'
  readonly form?: ConfigPageForm
}
interface ConfigPageForm {
  readonly state: ConfigFormSnapshot<Record<string, unknown>>
  readonly mutate: ConfigForm['mutate']
}
```

`ConfigFormSnapshot`：`{ status: 'loading'|'ready'|'unavailable', value, base, user, revision, writable }`——`value` 是宿主解析后的当前配置，`revision` 是写入门闩。

**注意 `form` 不是那个控制器**：真正持有快照的是 `dsh-client-ui-settings` 的 `ConfigFormController`（只有 `getSnapshot()` / `subscribe()`，没有 `.state`），但「插件」面板在渲染前把它包成了 `{ state: form.getSnapshot(), mutate }` 再交给槽位。所以 `plugin/client.js` 读 `form.state` 是对的；2026-10-29 有一份只读审核报告据此判「`form.state` 不存在、页面必空」，那是漏看了 `formFor` 这层包装，**不是 bug，别按那个建议改成 `getSnapshot()`**。


`mutate(ops: readonly SettingsPathOpView[], expectedRevision?: number): Promise<boolean>`；`SettingsPathOpView` 只有两种：

```ts
{ op: 'set'; path: string[]; value: JsonValue } | { op: 'unset'; path: string[] }
```

**一次 mutate 里的所有操作共用一个 revision、一次宿主校验、一次恢复读**；返回 `true` 表示宿主接受，`false` 表示拒绝（值非法或被跳过，宿主会重新读一遍）。`path` 为空数组表示整段根。

### 21.3 我们的实现

- `plugin/client.js`：`window.__ModuleLoader__.load({ id: 'dsh-ebbing-context', factory(require) {...} })`，在 `apply` 里 `ctx.slots.inject('plugins.row.config', ...)`（**不是** `plugins.bundle.config`：bundle 详情页 `renderSlot(..., { view: 'page' })` 不传 `form`，只有行详情页传 `{ view: 'page', form }`；key 用 `<包名>#<行 id>`） + `ctx.slots.register({ name, key })`（模板见 `templates/decoration/client.js`；`dsh.client` 段与 `./client` 导出见 `templates/decoration/package.json`）。
- **15 个控件**：budget 3（占比）、segment 3 + title 1（单块上限）、notice 2（开关 + 增长阈值）、`triggerPct`、`keepTurns`、`pruneFirst`、`foldCallRecord`、`requireSessionQuery`、`reservedTokens`。每项都是一个 `volatile` 叶子（见 §21.1 的 `volatileForm` 要求）。
- **草稿式**：改动只进本地草稿，最下面一个「保存」按钮统一提交；旁边有「放弃修改」与「待保存 N 项」。离开页面不保存。
- 保存 = 一次 `mutate(ops[], state.revision)`，所有改动**原子生效**：要么全成功，要么全不生效，不会出现改了一半。
- 提交前先本地校验（必填、数字、最小/最大）；不合法就**不提交**，并在页面顶部横幅列出「哪几项、为什么」。
- 宿主拒绝（`mutate` 返回 `false`）时顶部横幅写「宿主拒绝了这次保存，改动没有生效」——**宿主这个接口只回 true/false，不回原因**，所以拿不到它的具体拒绝理由；精确原因只能靠本地校验和插件启动时的 `validateConfig()` 报错。
- 每个设置项后面有一个「详情 / 收起」开关，展开后显示该项的完整说明。
- `state.writable === false` 时整页只读。
- **`form` 为 `undefined` 时不能只说"正在读取"**：宿主侧插件根本没启动（loader 的 import 失败被吞成一行日志，`ref\upstream\installed\cordis-plugin-loader.index.js:452-456` 的 `this.ctx.logger.error(error); return;`），插件行会停在「未运行」而不是「运行中」。所以这个页面等 4 秒仍拿不到 `form`，就改说"宿主侧没有启动起来、去看日志里的 import 错误"——否则用户对着一片空白无从下手。
- 页面不读文件、不调模型。显示值 = **宿主值打底、未保存草稿覆盖**：没有草稿时读 `form.state.value`，有草稿时读草稿；点「放弃修改」清掉草稿即回到宿主值。
- **页面最上方有一条常驻的「使用注意」**（`plugin/client.js` 的 `TEXT.note` + `noteStyle`，不折叠、不随草稿变化）：提醒关掉宿主自带的自动压缩（`compaction-basic` 的 `auto`，默认 80% 触发）。理由写在上面那段文案里：它一触发会把多层摘要重新拍平成一段高层摘要、原有细节永久丢失；插件本身不受影响，但效果打折。这条是纯提示，不改任何配置——我们不能替用户改宿主那行（它在 `group` 里，跨组按 `id` 覆盖会连带改 `isolate`）。
- **面板文案不许写本机细节，也不许写死配置入口**（2026-10-30 用户当场指出，`m13060`）：文案里曾出现"（本机 desktop profile 已经是 false）"和"关法：在 profile 的 `cordis.patch.yml` 里给 compaction-basic 那行写 `config: { auto: false }`"——前者把我们这台机器的配置当成通用事实，后者假定所有人都用同一套 profile/预设（`cordis` 那套只是其中一种）。现在只说"会发生什么"与"确认内置压缩不再自动触发即可"，位置交给用户按自己的安装去关。同理适用于所有 `detail`：只描述插件自己的行为与代价，不描述本机环境。
- **`detail` 不替模型下命令，也不许暗示"缩短"**（同日 `m13136` 指出）：曾写成"超过就要求模型拆成两次压缩，或写短一点"——"两次"是我们猜的数（实际可能要三次），"写短"会诱导它删内容换合格、直接拉低摘要质量。现在只说事实：超了整批拒绝、拒绝里给出实际值与上限，怎么调整由模型自己判断，并明说不要为了塞进上限删内容。
- **建议关掉宿主功能时，要写清"关的是什么"并给一句可复制的话**（同日 `m13173` 指出）：先前把"（本机已经是 false）"和写死的 `cordis.patch.yml` 一并删掉之后，文案退化成只说"关掉它"，用户不知道关哪里。现在三件事都写：关的是哪个行为（`compaction-basic` 的自动压缩 / 那个 `auto` 开关）、不关的后果只是效果打折、以及一句可以直接发给助手或模型的话（"帮我关掉……改完告诉我你动了哪个文件、怎么改回去"）——入口随安装方式而变，就让本来就有本机权限的模型去找。
- **配额类文案必须写"整层合计"**（同日 `m13136`）：`budget.*` 比的是整层 token 之和，不是单块；L3 还曾多写一句"它不会自己长大"——三层都不会自己长大，单拿 L3 说事只会让人以为 L1/L2 会。L3 的特别之处只有一个，且必须说准：压 `l2` 时新块追加在末尾、旧 L3 块不动，但**压 `l3` 时整个 L3 区并成一块、旧块一起并进去**（旧 L3 不会一直在）。
- **布尔开关的文案要写清"它改什么、不改什么"**（同日 `m13136`）：`requireSessionQuery` 曾写成"关掉则不管有没有取回工具都允许压"，读起来像开关改变了压缩行为——它其实只在"没有取回工具时要不要停用两个工具"上起作用，开与关 `compress` 都照常工作。同理 `notice.enabled` 不要在总开关里重述三条触发条件（`growthTokens` 那条已经单列，重复读起来像两个独立系统）。

### 21.4 与 YAML 的关系

面板保存写到 **profile 的 `cordis.patch.yml` 里的普通覆盖行**（`id` + `name` + 完整 `config`），**不改 bundle 的 patch，也不是 `insert` 行**。宿主以「该行当前完整配置」为底再做改动，所以不会因为只改一个字段就丢掉其他字段；当配置与继承值完全相等时，宿主先删 `row.config`（`dsh-config-editor/lib/index.js:99-104`）；只有该行仅剩 `id`/`name` 时才把**整行**删掉，行上的 `disabled`/`inject`/`isolate` 等元数据会保留。面板与手写 YAML 是同一份配置的两个入口，面板写入由**宿主 schema** 校验（`dsh-settings` 的 `mutate`）；`validateConfig()` 只在**插件启动**时跑，YAML 启动也一样。纯配置改动时宿主只更新引用、不重新 apply，所以那一次**不会**再跑 `validateConfig()`——目前两者合法域一致，故不构成风险。

### 21.5 尚未验证

浏览器侧代码**只能在装进 profile 之后**才被加载——本轮只做了语法检查（`node --check plugin/client.js` 通过）与本机槽位契约核对（`Slots.listSubTree` 查到 `plugins.bundle.config` 为 keyed、scope root、`view: 'page'`）。**能不能正常渲染、表单能不能保存，必须装机后到「插件」面板看。**

## 27. 真机首轮：`compress` 的参数 schema（0.1.1，2026-10-30）

首次真机运行报：

```
Invalid schema for function 'compress': true is not of type "array"
```

整轮请求被拒——插件装上了、工具也注册了，但模型一句话都发不出去。

**成因**：`compress` 的四个键（`l0`/`l1`/`l2`/`l3`）是嵌套对象，0.1.0 在它们的属性上写了 `required: true`。宿主只把**顶层** properties 的布尔 `required` 折成父级数组（`dsh-tools` 的 `parameterSchemaSpecToJsonSchema()`），嵌套层原样透传给 provider；OpenAI 兼容线要求 `required` 是字符串数组，看到 `true` 就整轮失败。

**规则（写代码时照这条）**：
1. 嵌套对象自身写 `required: ["title","summary"]`（`l0`/`l1`/`l2` 另加 `"to"`），**不要**在嵌套属性上写 `required: true`。
2. 宿主 raw-schema 边界（`dsh-tools` 的 `assertSupportedJsonSchema()`）：`required` 必须是字符串数组、数组里的名字必须在 `properties` 里声明过、`additionalProperties` 出现时必须是布尔、只许出现 `type`/`oneOf`/`properties`/`required`/`additionalProperties`/`items`/`enum`/`const` + `description`/`title`/`default`/`examples`。
3. 顶层 `properties` 可以不写 `required`（四个键都可选，模型按需给哪个层）。

**落地**：`plugin/index.js` 的 `blockSpec()`；回归断言在 `plugin/test/prestep.test.mjs` 第 2 项（按上面三条逐节点校验整棵参数树）。**代价提醒**：这类错误的单测全绿也发现不了——只有 provider 会拒；所以任何工具参数结构的改动都要过这条断言。
